# 全球情报聚合与 AI 内容发布系统 V2.0 升级需求

## 一、角色与总体目标

你是一名资深全栈架构师、AI Agent 工程师、数据工程师及 UI/UX 设计师。

请基于当前已有项目，完成一次系统性的功能升级。

系统定位为：

**多渠道全球情报采集 → 信息清洗与去重 → AI 价值分析 → 内容管理 → 多平台发布 → 数据反馈与可视化分析**

支持的信息渠道包括但不限于：

- X（Twitter）
- Truth Social
- Binance Square
- OKX Square
- 全球新闻媒体与 RSS
- 加密货币行业媒体
- 其他现有或未来可扩展的信息渠道

核心要求：

1. 保留当前项目架构、技术栈、数据库和已实现功能。
2. 优先复用现有模块，避免重复开发。
3. 所有新增功能必须具备真实的前后端交互，不允许只实现静态 UI。
4. 保持模块化、可扩展性和稳定性。
5. 实现完整的异常处理、操作日志和权限校验。
6. 开发前先分析代码与数据库结构，输出增量实施计划。
7. 不得未经允许删除原有数据或执行破坏性数据库操作。

## 二、优化模块 1：翻译功能调整

### 目标

取消系统自动翻译机制，改为用户主动触发翻译，降低不必要的 Token 消耗和后台请求。

### 功能要求

**1. 关闭自动翻译**

- 信息采集完成后，保留原始语言内容。
- 不再自动调用翻译 API。
- 不在默认采集流程中触发翻译任务。
- 保留现有翻译服务能力及相关配置。

**2. 新增手动翻译交互**

在文章卡片、文章详情、内容编辑器中加入：

- 「翻译」按钮
- 「查看原文」按钮
- 翻译目标语言选择
- 翻译中的 Loading 状态
- 翻译失败后的重试功能

**3. 优化翻译缓存**

- 相同文章与目标语言优先复用已保存译文。
- 原文发生变更时，使旧缓存失效。
- 支持原文和译文之间快速切换。
- 翻译请求必须由用户显式操作触发。

### 验收标准

采集文章后不产生自动翻译请求。用户点击翻译后才调用翻译服务，且不影响原始文章。

## 三、优化模块 2：发布中心重构

### 目标

将发布中心从单一的内容产出页面升级为完整的内容生命周期管理平台。

### 功能要求

**1. 完整的文章管理能力**

增加以下功能：

- 单篇文章删除
- 多选批量删除
- 当前筛选结果全选
- 一键清空发布中心
- 批量修改状态
- 内容搜索与筛选
- 按时间、渠道、状态排序

**2. 发布状态管理**

统一管理以下状态：

- 草稿
- 待审核
- 待发布
- 发布中
- 发布成功
- 发布失败
- 已归档

必须区分本地记录删除与第三方平台已发布内容的删除。

**3. 删除机制**

普通删除：

- 默认采用软删除。
- 删除后进入回收站。
- 支持恢复与彻底删除。

批量删除：

- 支持多选记录。
- 展示删除数量。
- 执行前显示确认对话框。
- 批量操作应使用服务端接口，避免大量并发单条请求。

一键清空：

- 提供独立的「清空发布中心」入口。
- 必须进行二次确认。
- 默认仅清理用户有权限管理的本地内容。
- 不得自动删除第三方平台已经发布的内容。
- 不得影响情报采集数据库中的原始文章。

**4. 发布历史与操作日志**

- 查看发布平台、发布时间和发布状态。
- 保存平台返回的文章 ID 和 URL。
- 记录发布失败原因。
- 支持失败任务重试。
- 对删除、清空、发布等操作记录审计日志。

### 验收标准

用户可以完成单条删除、批量删除、一键清空和恢复操作，数据状态在前后端保持一致。

## 四、优化模块 3：Agent 全系统集成

### 目标

Agent 不应仅是单独的聊天模块，而应该能够理解并操作整个系统，通过 LLM 统一编排信息获取、情报分析、文章创作和多平台发布流程。

### 架构建议

采用可扩展的 Agent + Tool Calling 模式。

Agent 通过经过权限控制的标准化工具访问系统服务，不应直接拥有无限制数据库读写权限。

### 功能要求

**1. Agent 全局访问入口**

在系统主导航中增加 AI Agent 工作台。

同时，在以下页面提供 Agent 快捷入口：

- 情报采集中心
- 文章详情页面
- 发布中心
- 数据分析中心

Agent 需具备页面上下文感知能力，能够知道用户当前选中的文章、筛选条件或分析对象。

**2. Agent 工具系统**

提供以下工具能力：

| 工具 | 功能 |
|---|---|
| search_articles | 搜索已采集文章 |
| get_article_detail | 获取文章详情 |
| summarize_article | 提炼文章核心内容 |
| extract_insights | 提取有价值的信息 |
| compare_sources | 跨平台交叉验证 |
| analyze_sentiment | 分析情绪倾向 |
| detect_duplicates | 检测重复与相似文章 |
| generate_post | 生成适合目标平台的文案 |
| create_draft | 创建发布草稿 |
| publish_post | 发布已授权内容 |
| get_publish_status | 查询发布状态 |
| analyze_channels | 获取不同渠道的统计结果 |

工具名称可根据项目现有架构调整，但职责应清晰且可复用。

**3. Agent 自然语言控制**

支持如下指令：

“分析最近 24 小时 X 上关于 BTC 的高价值信息，筛选最值得关注的 10 条。”

“提取这篇文章的核心观点，并分析它可能对黄金和加密货币市场产生的影响。”

“根据最近 12 小时的行业热点生成一篇适合 Binance Square 的中文文章。”

“比较 Truth Social 和 X 上关于美联储政策的信息差异。”

“把这 5 篇文章整合成一篇有独立观点的深度分析，并保存到草稿箱。”

**4. Agent 内容价值提取**

针对文章输出结构化分析：

- 核心事件
- 事实摘要
- 关键实体
- 信息来源
- 事件发生时间
- 发布时间
- 影响范围
- 可信度等级
- 情绪方向
- 市场潜在影响
- 值得关注的原因
- 建议的后续观察指标

区分事实、来源观点与 AI 推测，不得将推测包装为确定事实。

**5. Agent 发布工作流**

完整流程：

用户任务 → Agent 理解意图 → 检索相关文章 → 提取关键信息 → 生成文案 → 用户审核 → 调用平台发布工具 → 返回发布结果。

重要要求：

- 默认采用人工审核后发布。
- 自动发布必须有单独的授权开关与平台级权限。
- 所有公开发布操作具备审计记录。
- 发布失败应可恢复、重试，并实现幂等保护。
- 不允许未经授权直接调用外部平台发布。
- 遵守目标平台 API 权限、内容政策与速率限制。

**6. Agent 执行可观测性**

展示：

- 当前执行步骤
- 已调用工具
- 工具调用结果
- Token 用量
- 推理及工具成本估算
- 错误原因
- 最终任务状态

### 验收标准

Agent 能够真实调用系统服务，完成从文章搜索、价值提取、文案生成到审核发布的端到端工作流。

## 六、优化模块 5：多渠道可视化分析中心

### 目标

构建独立的 Analytics Dashboard，对不同渠道的文章、热点、有效信息及传播趋势进行统一的量化分析。

不应只统计文章数量，而应帮助用户发现真正值得关注的信息。

### 1. 多渠道数据统计

提供以下指标：

- 总采集文章数
- 有效文章数
- 去重文章数
- 低价值过滤数
- 各渠道文章占比
- 高价值文章数量
- 热点事件数量
- 来源可信度分布
- 已生成草稿数
- 已发布文章数
- 发布成功率

支持时间范围筛选：

- 最近 1 小时
- 最近 24 小时
- 最近 7 天
- 最近 30 天
- 自定义时间范围

### 2. 图表展示

需要实现：

**渠道信息分布图**

显示 X、Truth Social、Binance Square、OKX Square 和新闻媒体等渠道的信息数量及占比。

**信息价值趋势图**

展示不同时间区间内高价值、中等价值与低价值文章的变化。

**热点主题排行榜**

例如：

- BTC
- ETH
- 美联储
- 黄金
- AI
- 全球宏观经济

主题应由实际数据动态生成，不允许将示例主题写死。

**信息情绪分析图**

展示正面、中性、负面及无法判断的信息占比，并说明情绪分类针对的是文章语义还是特定资产。

**跨平台热点对比**

识别同一个事件在不同渠道中的：

- 首次出现时间
- 讨论热度
- 传播数量
- 信息观点差异
- 相似文章数量

不得将采样到的文章数量直接冒充全平台真实热度。

### 3. AI 信息价值评分

引入 Information Value Score，范围 0–100。

建议初始评分维度：

| 评分维度 | 权重 |
|---|---:|
| 信息来源可信度 | 25% |
| 时效性 | 20% |
| 对关注领域的潜在影响 | 25% |
| 信息新颖程度 | 20% |
| 可验证性与证据完整度 | 10% |

以上为初始可配置权重，并非最终经过验证的模型。

评分要求：

- 明确展示评分理由。
- 支持用户调整权重。
- 支持根据用户反馈优化评分。
- 记录评分模型版本。
- 不得把 AI 评分当作事实真实性证明。
- 没有足够证据时，显示「待验证」。

### 4. 无意义信息过滤

建立多层过滤系统：

**第一层：规则过滤**

- 广告
- 明显垃圾信息
- 重复内容
- 无实质内容的转发
- 纯营销文案
- 非目标语言或非目标领域内容（可配置）

**第二层：语义过滤**

通过向量相似度或语义匹配识别：

- 相同事件的重复报道
- 轻微改写的重复文章
- 无新增事实的信息
- 与用户关注主题无关的内容

**第三层：AI 价值评估**

识别文章是否提供：

- 新事实
- 新数据
- 原始信源
- 重要人物观点
- 政策变化
- 市场结构变化
- 具有可验证依据的潜在影响

**第四层：人工反馈**

用户可标记：

- 有价值
- 无价值
- 不感兴趣
- 错误过滤
- 来源不可信

反馈用于调整后续排序与过滤参数。

### 5. 过滤操作机制

支持：

- 按渠道过滤
- 按关键词过滤
- 按主题过滤
- 按价值评分过滤
- 按可信度过滤
- 按情绪过滤
- 按时间过滤
- 按语言过滤
- 自定义黑白名单

重要：

默认采用隐藏或隔离低价值信息的方式，不直接删除原始采集数据。

支持查看被过滤信息及恢复。

## 七、建议新增：AI 情报工作流

为了提高系统价值，增加统一的情报处理 Pipeline。

采集信息
↓
统一格式与字段标准化
↓
规则过滤
↓
内容去重
↓
语义聚类
↓
AI 价值评分
↓
重点事件提取
↓
可视化分析
↓
Agent 生成内容
↓
人工审核
↓
多平台发布
↓
发布结果记录与分析

架构要求：

1. 数据采集与 AI 分析解耦。
2. 重复内容优先使用低成本规则和语义算法处理。
3. 不要对所有文章无差别调用大模型。
4. LLM 仅处理需要深度推理或内容生成的任务。
5. 每个处理阶段应具有可追踪状态。
6. 后台任务要有重试、超时和失败隔离机制。
7. 同一事件可以关联多个来源，但原始文章必须保留。
8. 统计数据应能按时间、渠道、主题和处理结果聚合。

## 八、系统架构与安全要求

请根据现有技术栈实现，不要为了新功能盲目引入复杂框架。

必须考虑：

- 数据库迁移及向后兼容
- Agent 工具权限与身份认证
- API 密钥安全管理
- 发布操作权限校验
- 外部采集内容的 Prompt Injection 防护
- AI 生成内容的事实检查与来源追踪
- 大规模文章列表的分页与查询性能
- 高成本 LLM 请求的缓存与限流
- 采集任务与发布任务的解耦
- 各平台接口错误处理与调用配额管理

对于尚未拥有 API 访问权限的平台，只实现合法可用的适配层或明确标记为待接入，不允许伪造发布成功结果。

## 十、Codex 工作要求

请按以下方式开展工作：

1. 先检查项目实际代码，不要假设已有不存在的功能。
2. 先制定可验证的实施计划，再逐模块修改代码。
3. 发现需求与现有架构冲突时，优先提出兼容性改造方案。
4. 能复用的模块不得重复实现。
5. 所有接口必须连接真实业务逻辑，禁止只做展示性假数据。
6. 新增配置必须提供清晰的环境变量说明。
7. 数据库结构修改必须具有迁移与回滚方案。
8. 每完成一个模块，运行对应测试并修复发现的问题。
9. 不得清空现有数据库或重置生产数据。
10. 未经授权不得执行真实的公开发布或其他不可逆外部操作。

最终交付：

- 已实施的功能与对应代码文件
- 新增或修改的 API
- 数据库迁移说明
- 新增环境变量配置
- 测试结果
- 未完成项及原因
- 部署和升级说明

**最终目标：将当前系统升级为一个能够自动化采集、智能筛选、深度分析、可视化展示，并由 AI Agent 统一编排和辅助发布的全球情报管理平台。**
